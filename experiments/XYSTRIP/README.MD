## Recommendation

Qualify the 2,816-byte staged budget first. It admits X24, Y16, X16/Y8,
and X8/Y12, instead of falling immediately to a blanked full conversion.
Use X16/Y8 as the initial continuous-movement step, optionally X24 for a
horizontal fast step. It adds 1,376 bytes of scratch and 86 bytes of assembled
code (1,462 bytes before segment/file alignment). It allocates nothing per pan.

The 5,504-byte variant is the faster candidate in this emulator: X48 or Y32,
and X32/Y16 diagonals, still complete in one approximately 16.5 ms frame.
It needs 4,064 extra scratch bytes plus the same 86 code bytes. Treat this as
the next speed preset to qualify, not a proven optimum for a physical 7.16 MHz
8088. Its extra memory cost and longer preconversion need Windows/640K tests.
The exact tracked-source patch supplied here selects 2,816 bytes; the larger
variant is explicitly generated by NATIVE.PY's `--budget 5504` option.

Also qualify the pure-Y4 no-blank path in the patch. Every one of its 640
destination bytes is offscreen in the OLD viewport, for every legal origin
and either direction. Commit those bytes while the old view is visible, then
use the existing retrace-synchronized CRTC change. The old cursor is hidden
before either logical origin changes. Presentation failure now explicitly
blanks before converting the software fallback, including this new path.

Do not change the helper's 8/4 defaults solely from these measurements. Test
X16/Y8 and X32/Y16 on the target first, with the actual Windows scheduling,
input repeat/edge timer, cursor and desktop drawing workload.

## Facts verified in current main

* Logical desktop 640x256; physical view 320x200; X quantized to 8, Y to 4;
  legal origins X=0..320 and Y=0..56. XYCTL keys, edge and combined control
  paths use 8/4 steps; overview/follow can request larger aligned jumps.
* The XY hardware path accepts abs(dx)<=8 and abs(dy)<=4. Other changes use
  the guarded full path. The older HPAN horizontal experiment differs: it can
  convert larger horizontal strips while blanked. It is not the XY policy.
* Current small moves stage 800 horizontal, 640 vertical or 1,440 diagonal
  packed bytes before blanking. The diagonal includes its 16-byte corner twice.
* Sequence: hide old cursor; change logical state/head; stage; blank; commit;
  wait for retrace OFF then ON; write CRTC start; unblank; restore cursor.
* Full fallback converts and copies 32,000 bytes while blanked, then waits.
* Canonical planar shadow remains 64,000+17,920=81,920 bytes. No geometry,
  bank size, color depth, ownership guard or other adapter is changed here.

## Exact work and alias proof

Let X=abs(dx), Y=abs(dy), after clamping/quantization. For disjoint strips:

    B = 100*X + 160*Y - X*Y/2 packed bytes

The vertical strip owns the diagonal corner; the horizontal strip spans only
the shared Y interval. The new gate calculates B BEFORE staging and admits
only B<=2,816. Geometry guarantees 0<=B<=32,000, so 16-bit arithmetic cannot
wrap. The scratch allocation, producer's comment and post-stage bound agree.
This is a storage/work budget, not a raised distance threshold.

For logical packed byte x and row y, the physical address is:

    bank = (y & 3)*8192
    offset = (floor(y/4)*160 + x) & 8191

Because both Y origins are multiples of four, retained logical pixels have
the same address in both views. Each view occupies 8,000 distinct bytes in
each 8,192-byte bank; the 192-byte gap is the only generally safe prewrite
space. Groups begin on four-byte boundaries; two MOVSWs cannot cross a bank
before the existing mask restores the bank offset. The shadow row accessor
keeps rows 0..199 and 200..255 in their separate segment allocations.

| Move | Unique staged | Old-offscreen destinations | Old-visible destinations |
| --- | ---: | ---: | ---: |
| X8 | 800 | 16 | 784 |
| Y4 | 640 | 640 | 0 |
| Y8 | 1,280 | 768 | 512 |
| X8/Y4 | 1,424 | 656 | 768 |
| X16/Y8 | 2,816 | 768 | 2,048 |
| X32/Y16 | 5,504 | 768 | 4,736 |

Thus preconverting every strip is safe; prewriting arbitrary whole strips is
not. The patch prewrites only the proved Y4 case. A future safe/unsafe split
could move at most 768 bytes out of the blanked commit; for X-only moves the
benefit is tiny. Never precommit an entire horizontal strip while visible.

## Retrace placement and the minimum-blank tradeoff

The current wait is the dominant staged blackout. In the 2,816-byte run,
X16/Y8 commits in about 0.47 ms but remains blank about 12.12 ms. In the
5,504-byte run, X32/Y16 commits in about 0.71 ms but remains blank 8.31 ms.
These are timer-instrumented emulator phase measurements, not 8088 estimates.

Moving the OFF->ON wait before blanking can theoretically reduce black time
to commit + CRTC/unblank I/O, if that entire transaction fits the retrace
window with a proved margin. The present hp_present routine cannot simply be
called again after that commit: it deliberately waits OUT of active retrace
and for a NEW edge, potentially adding another whole frame. A future path
must split wait-for-edge from write-start and retain a bounded missed-deadline
fallback while still blanked. Accepting any asserted retrace bit without a
timing margin can race its end. Writing immediately without proving latch/
scanout behavior is not justified by a framebuffer dump.

This investigation leaves the common retrace code unchanged. No shortened-
wait native variant is claimed tested. On the physical shared-memory 8088,
commit address arithmetic, VRAM waits, interrupt latency and actual retrace
width can invalidate the emulator's apparent sub-millisecond opportunity.
Y4 avoids this timing gamble because every write is outside the old view.

## Bounded moves versus direct jumps

The independent host dynamic-programming model compares walks that retain
correct intermediate views. It minimizes transaction count, then staged bytes.
For a requested X32/Y16 jump, two X16/Y8 transactions stage 5,632 bytes with
the small budget; one large transaction stages 5,504 bytes. For X320/Y56,
the small budget needs 16 transactions / 40,512 staged bytes; the large budget
needs 8 / 39,840. At a hypothetical 60 successful updates/s those take about
267 or 133 ms, versus roughly 51 ms for one emulator full-copy call. Chunking
reduces each blackout and preserves responsiveness, but can slow arrival at a
distant target and increases total conversion work. These walk times are a
host scheduling model, not measured end-to-end helper behavior.

For smooth far-target animation, retain a target and issue one bounded hop
per timer callback, re-querying the actual origin and coalescing newer input.
Do not run an unbounded synchronous chain inside Escape, hide the cursor
across a long animation, or commit final-target chunks into visible memory.
Keep a deliberate direct-jump/full-copy option for fastest distant arrival.
No helper chunking policy is implemented in this patch. Thus requests above
the staged budget still take the existing safe full fallback.

## Host checks, limits and next step

MODEL.C passes 96,196 admitted/clamped moves over all 615 legal origins,
both signs, diagonals, edges, 8K bank wrap and both planar shadow bands:
3,078,272,000 destination-byte comparisons. It checks old-view preservation
during offscreen prewrites and exact final equivalence to a full conversion.
This is an independent content/address model, not instruction execution or
scanout. The original narrower 48,688-case receipt is MODEL48.JSN.

The final native runs execute the assembly, including high origins and both
directions, but only compare settled VRAM, not optical blackout or CRTC latch
timing. They use FAR cursor stubs; actual Windows cursor drawing, interactive
GDI ordering, keyboard/mouse use and low-memory behavior remain untested.
The existing legacy hp_last_cols staged-path marker remains 8; use the exact
hp_last_bytes counter for this experiment's workload measurements.

Early `native-base` and `native-base-02` attempts retain MASM harness failures
(forward FAR/SEG declaration order); the product source was not the cause.
The `*-03` framebuffer results passed, but their mode-3 PIT timing is INVALID
because counter phase was ambiguous. Final `*-05` tests use mode 2 at the
same BIOS tick frequency and reject reversed or implausible timer samples.
No timer values from the invalid runs support this recommendation.

Next: build the complete private HPXY overlay from its pinned dependency
view; update private build metadata to the selected scratch size (XRBUILD's
historical report still says 1,440); qualify in Windows 3.0 real mode with
visible cursor and ordinary GDI redraws. Test reversals, edges, bank-wrap
origins, overview jumps, fault/timeouts and allocation headroom. Then measure
PIT/port blank intervals and visible frames on an EX 8088 at 7.16 MHz before
choosing 2,816 versus 5,504 or enabling an earlier-retrace optimization.

Reproduce host checks with the mandatory managed GCC wrapper, `-std=c89 -O2
-Wall -Wextra -Werror`, then MODEL.EXE and ANALYZE.PY. NATIVE.PY has explicit
prepare/run/verify actions. Every run uses the existing shared nonblocking
lease via RUNDOS.PY, a new private directory, hidden child, owned watchdog,
process inventory and verified stop. No frame-capture stream was generated;
only fixed 32 KiB VRAM dumps and capped trace buffers are retained. Do not
reuse an output directory or run a native action without its lease.
