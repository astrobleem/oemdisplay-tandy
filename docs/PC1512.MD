# Windows 3.0 on Amstrad PC1512

**[Download P15SET.EXE](https://raw.githubusercontent.com/astrobleem/oemdisplay-tandy/main/downloads/experimental/PC1512/P15SET.EXE)**

For PC1512 built-in video, 8086, 640 KB, DOS 3.20+ and an installed Windows 3.0.
Not PC1640 or ordinary CGA. The driver, matching original fonts, grabber and
startup logos are included. Dedicated video RAM needs no reservation helper.

1. Copy P15SET.EXE to the PC1512. Exit Windows to DOS and run `P15SET`.
2. Run `C:\P15EXP\INSTALL`.
3. In Setup choose Display, Other, `C:\P15EXP`, then
   **Amstrad PC1512 640x200 16 colors**. Complete Setup and return to DOS.
4. Start Windows with `C:\P15EXP\P15WIN`.

Windows defaults to `C:\WINDOWS`. For another directory, pass its drive and
path to both entries, for example `INSTALL D: \WIN30` and `P15WIN D: \WIN30`.

[ZIP alternative](https://raw.githubusercontent.com/astrobleem/oemdisplay-tandy/main/downloads/experimental/PC1512/PC1512.ZIP) |

## Target hardware

The Amstrad PC1512 (1986): 8 MHz 8086, CGA-compatible video built into the
motherboard, plus one extra mode, 640x200 in 16 colours, which the original
machine used only for GEM. There was no Windows driver for it; Windows ran
in CGA monochrome. This driver is only for that machine (and its clones'
identical video, if any). The PC1640 has an EGA-class chip instead and is
not a target.

## Hardware model

From the seasip.info PC1512 display notes and 86Box `src/machine/m_amstrad.c`,
which agree:

- ROS INT 10h mode 6 (CGA 640x200), then port 3D9h = 0Fh to show all four
  planes (the ROS leaves 7, so intensity is hidden). Switched with
  interrupts off, during vertical flyback.
- Four 16KB bit-planes share the CGA window at B800h, each in CGA layout:
  even rows at +0000h, odd rows at +2000h, 80 bytes per row, leftmost
  pixel in bit 7. Plane bits: 0 blue, 1 green, 2 red, 3 intensity.
- Port 3DDh (write-only) is a plane write mask: a CPU write lands in every
  selected plane. Port 3DEh (write-only, low two bits) selects the one
  plane that CPU reads return.

## How the driver is built

The TR5 renderer draws everything into a private shadow of four planes
per row in DDK order red, green, blue, intensity, and only copies to video
memory when flushing. At 640 wide each shadow plane row is 80 bytes, exactly
one PC1512 plane row, so a flush is four straight copies per row: red with
3DDh = 4, green 2, blue 1, intensity 8.

`src/pc1512/BUILD15.PY` (pinned inputs as BUILD88; see Reproducing):

1. Runs BUILD88 unchanged for 320x200x16 (the accepted TANDY88 profile;
   its driver hash is recorded).
2. Runs BUILD88 unchanged for 640x200x4, so every 640-pixel stage and every
   BUILD88 pin is exercised as-is: geometry, CGA fonts and metrics, byte
   columns, cursor retention, output rows, wide scanlines, REP-copy rewriting,
   resources.
3. Between staging and the first assembly of step 2 it puts the sixteen
   colours back: the six files the four-colour mapper rewrote, and its
   TSOFT colour-table sections, are replaced by the 320x200x16 stage copies
   (`P15PATCH.restore_sixteen`). Then `src/pc1512/P15PATCH.PY` edits the
   staged EGA/TSOFT.ASM and EGA/TCURSOR.ASM, each edit with an exact match
   count:

| Area | Change |
| --- | --- |
| Four flush routines | CGA two-bank row address (80-byte rows) instead of Tandy four-bank (160); `p15_row` copies the four shadow planes through 3DDh |
| Cursor retention | physical columns are plane bytes (80 per row); the Tandy x2 column scale is gone |
| `TEnable` / `TDisable` | mode 6, flyback wait, 3D9h = 0Fh, 3DDh = 0Fh, 3DEh = 0, clear all planes; before leaving 3DDh = 0Fh, 3DEh = 0, 3D9h = 7, then the old mode |
| `TCURSOR` | CGA row math; the four planes under the cursor are saved through 3DEh (buffer 640 bytes), composited in a private copy (AND clears the pixel's bit in every plane, XOR flips it) and written back through 3DDh |

The cursor needs no colour decoding: AND forces colour 0 and XOR flips all
four colour bits, both bitwise per plane. Every path leaves 3DDh = 0Fh and
3DEh = 0. Video memory is on the motherboard but outside DOS memory, so no
reservation is needed.

BUILD88's instruction, REP-prefix and link audits run on the patched
listings and pass. Two clean builds gave the same driver:

    PC1512.DRV  54,448 bytes
    SHA256 31aca63699f05ef57094443de0b3f6926de2c516657aaabc5ee580ac4f65d9f7

Reports: `pc1512/P15RES.JSN`, `pc1512/P15RES2.JSN` (the second build).
`P15PATCH.PY --check` proves the flush on the host: a random full shadow
copied by the `p15_row` model and decoded with 86Box's PC1512 rules gives
every one of the 128,000 pixels' colours, and the ROS default 3D9h = 7
would not.

### The machine is a PC1512

`src/pc1512/P15ID.ASM` sets mode 6 and 3D9h = 0Fh, writes 11h, 22h, 44h, 88h
with the single-plane write masks 1, 2, 4, 8, reads each plane back
through 3DEh, then writes 5Ah with mask 0Fh and reads all four planes. Only
four separate planes behind 3DDh/3DEh give `PLANES=11,22,44,88
ALL=5A,5A,5A,5A PC1512=01` (`pc1512/P86NEG.JSN`):

| Run | Result |
| --- | --- |
| 86Box `pc1512`, at boot and after each Windows exit | `PLANES=11,22,44,88 ALL=5A,5A,5A,5A PC1512=01` |
| DOSBox-X `machine=cga` and `tandy`; DOSBox 0.74 `cga` and `tandy` | `PLANES=88,88,88,88` (one plane, last write wins) `PC1512=00` |

Before Windows, `P15SHOW` (generated by `P15TEST.PY` from the same text the
driver build inserts: enable sequence, row address, `p15_row`) drew 16 bars
that decode to exactly colours 0-15 in IRGB order (128,000 pixels, 0
mismatches), which settles plane order and bit order on this emulated

screen positions measured from exact frames of this machine (`PCPWIN.LAYOUTS[640]`).

### Pointer landing and cursor state

Final result: 88/88 final checks; of the 16 arrow-over-palette cases, 15
passed first try and 1 was recovered by a retry. Retries help test the
renderer, but they are reported, not hidden: PCPCHK's output carries
`palette_arrow_landing` (`pc1512/P86CHK.JSN`).

Two different kinds of failure were seen; their upstream causes remain
unresolved:

1. **Unexpected coordinates received at MoveCursor (diagnostic runs).**
   The first complete run (same driver, same script) failed 17
   checks, all in the arrow-over-palette group: in 5 of 16 frames the
   arrow was not where it had been sent, which also spoiled the shared-glyph
   check. `src/pc1512/P15DBG.PY` builds a diagnostic driver (never for use)
   that counts cursor calls, keeps the last 16 MoveCursor coordinates
   Windows passed, and writes them into screen rows 0 and 2 so the 86Box
   screenshot carries them (`pc1512/P86DBG.JSN`, `DBG1.PNG`, `DBG2.PNG`).
   On a fresh VM with Paintbrush maximized, the requested motion and the
   received coordinates differed: sent +362,+193 mickeys from (0,0),
   MoveCursor received
   (127,127) and then (180,195); all 8 cells tried showed x about half and
   y 2-3 more. The same coordinates arrived when MoveCursor never draws at
   interrupt time (`--defer`), and the normal build drew the arrow exactly
   at the received coordinates. No SetCursor was refused in those runs. It
   comes
   and goes: later in the same sessions the same moves landed exactly.
   This localizes the observed mismatch to the coordinates entering the
   drawing routine. It does not distinguish the input harness, mouse
   driver, Windows scaling/state or display-driver contract as the upstream
   cause, and does not prove every failure in the first run had that cause.
2. **Wrong cursor shape (the one retry in the final run).** Attempt 1 of
   `arrow_12` shows the cursor exactly at the requested position (222,186),
   but it is Paintbrush's crosshair, not the arrow (46 changed pixels around
   the hotspot; `pc1512/P86MISS.JSN`). That is cursor shape/state, not
   coordinates. Whether Windows did not ask for the arrow or the driver did
   not apply a shape change was not established: that run used the normal
   driver, which records no cursor calls. It stays an open question for
   the cursor code and for real hardware.

The harness gives every attempt its own frame (`arrow_NN_tK`); an attempt
that does not show the verified arrow exactly at the hotspot is logged with
its changed-pixel count and bounds. Bounds alone identify neither a cursor
shape nor a cause, so classifications remain neutral. The recorded crosshair
was identified separately by its exact translated XOR footprint, not just
its bounding box (`pc1512/P86MISS.JSN`). The move is sent again after 20 s,
at most 8 times; the first exact attempt becomes `arrow_NN`, judged by
PCPCHK with the same rule. The
final run predates per-attempt ids; its index (`pc1512/P86RAW.JSN`) names
both attempts separately, each matched to its own raw capture by decoding
it during curation. The repository retains ten decoded-source raw captures;
the two retry raw files are not retained, so their original decode cannot
be independently repeated from repository files alone. Their retained
pixel identities and capture order remain reviewable. The arrow over all
16 colours is also proven by the wallpaper frames,
which needed no retry. A real PC1512 would normally use its own mouse port
and driver, which this session did not test.

The host corrections do not represent a new guest run. The recorded
`P86CHK.JSN`, `P86LAND.JSN`, step log and image pixels remain unchanged:
88/88 final pixel/file checks, 15/16 first attempts, one recovery. Current
PCPWIN clears old accepted aliases and attempt images before a session,
records a fresh empty LANDING list, and stops on retry exhaustion. PCPCHK
additionally requires all 16 successful current attempts, checks each alias
against its attempt image and exact arrow composite, and verifies earlier
attempts did not already pass. Metadata errors force FAIL independently of
the 88 pixel/file checks; a stale alias cannot qualify an exhausted run.

`PCPEVID.PY` rejects duplicate frame IDs/raw-source names, invalid
accepted-from references, missing attempt sequences, alias pixel mismatches
and incorrect retained-raw bindings. PCPMUT validates this index before
loading it. Legacy Plantronics captures without retry aliases remain valid.

### Other findings

- **No major renderer defect found.** Nothing in the driver changed after
  the first build. The cursor-shape miss above is unexplained.
- Calculator at 200 lines: its memory indicator box (normally hidden
  behind the keys) shows as an empty frame over the `/` and `sqrt` keys;
  with a stored number it shows `M` (checked by storing 5). This is
  Calculator's own layout at this height, not a drawing error; it is not
  visible on the 320-wide Plantronics screen.
- The saved BMP stores the DDK colour table the driver inherits (light gray
  as 128,128,128, dark gray as 64,64,64), as with the Plantronics and Tandy
  drivers.
- 242K free in Windows real mode (Plantronics XT: 337K): the 640-wide
  shadow is 64,000 bytes.
